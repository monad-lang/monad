# The web profile: loader, runtime and an Oak SPA

The `wasm32-unknown-unknown` ("web") profile produces a freestanding
`.wasm` that a browser page instantiates with a JS import object.

## Files

| File | What it is |
|---|---|
| `web.js` | **Build artifact** (gitignored), generated by `scripts/gen-web-js.sh` from `examples/gen_web_js.mo` and `WebAbi` (`motes/web_wasm/src/web_abi.mo`). It builds the import object and exports `start(url, selector)`; never edit it. The script builds and runs the generator in a temp dir and sanity-checks the output; `build-try.sh` and both check scripts call it, so a fresh checkout generates it on demand. |
| `web_runtime.js` | The hand-written host behind those imports: DOM node table and reads (`nodeType`/lowercase `tagName`/form `value`/selector `query`), the current-event slot and its selector getters, listener specs/flags and the declarative drag/clipboard effects, window/document/frame listeners, async clipboard, fetch, storage, console/stdin, `F64.to_string` (the freestanding profile's float formatter), the `Keep` state slot and the `requestAnimationFrame` tick loop. |

## Running an SPA

A program exposes three `#[export "c"]` thunks and calls `motes/oak_wasm`'s
runtime (`fixtures/wasm/oak_spa.mo` is the worked example):

```monad
#[export "c"]
def oak_mount : IO Unit := Runtime.mount prog

#[export "c"]
def oak_dispatch_event (handler : I64) : IO Unit := Runtime.dispatch handler

#[export "c"]
def oak_tick : IO Unit := Runtime.tick app host
```

```bash
monad build --target wasm32-unknown-unknown fixtures/wasm/oak_spa.mo -o app.wasm
```

```html
<script type="module">
  import { start } from './web.js';
  start('./app.wasm', '#app');
</script>
```

`start` sets the mount selector, instantiates the module with the generated
import object, calls `oak_mount()` and starts the tick loop. On every frame
it first dispatches an animation-frame subscription (if the app declares
one), then `oak_tick` folds queued messages, re-renders and patches the DOM;
DOM listeners registered from `data-oak-on-<event>` attributes call
`oak_dispatch_event(id)`. Handler ids come from `Oak.lower` (path + event).

## Checking

`scripts/check-wasm-target.sh` builds and runs every one of these (it needs
`WASI_SDK_PATH`, `node` and `wasmtime`), and runs in CI as the WASM target
proof. It generates `web.js` with `scripts/gen-web-js.sh` before the first
harness that imports it; a fresh checkout has no copy.

## The browser REPL (`/try`)

`https://monad-lang.org/try` runs one Monad module in the browser, using the
self-hosted compiler's own front end compiled to wasm. Two modules:

- `motes/try_engine` is DOM-free and runs in a Web Worker. Its evaluator is
  `eval::run`, the shared recipe `monad eval` and `monad repl` use; /try
  supplies the served sources and the fuel/depth policy, and never imports
  `eval::file`/`eval::session` (which would pull in the filesystem loader).
  It ships **no prelude**: the page fetches the real `init/src/*.mo` files served beside
  the wasm (`sources.json` indexes them), frames their text with
  `docs/site/static/try/sources.js`, and passes it as `try_run`'s first
  argument. `src/sources.mo` parses that payload into module identities (a
  served path names its module: `init/src/lib.mo` is `init`,
  `init/src/prelude.mo` is the ambient `prelude`, `init/src/number.mo` is
  `init.number`), so the program is checked against exactly the files the
  site ships. The engine's only browser import is `try_result`, which
  pushes the rendered result back to the host.
- `motes/try_ui` is the Oak page. It posts the scratchpad to the worker and
  polls `worker_poll` on its animation-frame subscription (a promise never
  re-enters wasm). Cancel terminates the worker, which is also the only way
  to stop a runaway loop.

`scripts/build-try.sh` builds both into `docs/site/static/try/` with the
generated host, the page shell, and the served prelude (`sources/` mirrored
at repo-relative paths plus `sources.json`, every non-test `init/src`
module); `scripts/check-try.sh` builds a temp directory and runs the
staging, worker, engine and UI harnesses. The directory is build output
(only the page shell, `worker.js` and `sources.js` are tracked), so run the
script (or `devenv`'s `docs-serve`, which does) after any checkout, and
restart `zola serve` afterwards -- it snapshots `static/` at startup. `docs/src/try.md` documents the user-facing rules
(`main`, prelude only, the two-million-step budget).
